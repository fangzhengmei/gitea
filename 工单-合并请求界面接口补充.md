本文档是 `issue-pr-shared-model-analysis.md` 的补充，重点分析界面层和 API 接口层的定制差异，以及这些差异如何与底层共享模型、合并/关闭分叉逻辑联动。

## 一、列表页面入口：路由级别的差异

### 1. Web 界面入口路由

**文件位置**：`routers/web/repo/issue_list.go:736-774`


**路由映射**：

| `/owner/repo/pulls` | `true` | `PageIsPullList` | `MustAllowPulls()` |

### 3. 与共享模型的联动

入口路由层通过 `optional.Some(isPullList)` 将类型标识传递给 `prepareIssueFilterAndList` 函数，该函数内部将 `IsPull` 条件传递给 `IssuesOptions`，最终在数据库查询层通过 `is_pull` 字段过滤：

```
路由层 URL 路径
    ↓
isPullList = (type == "pulls")
    ↓
prepareIssueFilterAndList(..., optional.Some(isPullList))
    ↓
IssuesOptions.IsPull = isPullOption
    ↓
isPullToCond() → builder.Eq{"is_pull": value}
    ↓
SQL WHERE is_pull = true/false
```

#### 第四步："等待我审查" 的 SQL 逻辑

**文件位置**：`models/issues/issue_search.go:393-416`

```go
func applyReviewRequestedCondition(sess *xorm.Session, reviewRequestedID int64) {
    // 子查询 1：找出用户所在的团队
    existInTeamQuery := builder.Select("team_user.team_id").
        From("team_user").
        Where(builder.Eq{"team_user.uid": reviewRequestedID})

    // 子查询 2：找出每个 PR 每个审查者的最新审查记录
    // 排除已批准或已拒绝的（这些不再需要审查）
    maxReview := builder.Select("MAX(r.id)").
        From("review as r").
        Where(builder.In("r.type", []ReviewType{ReviewTypeApprove, ReviewTypeReject, ReviewTypeRequest})).
        GroupBy("r.issue_id, r.reviewer_id, r.reviewer_team_id")

    // 子查询 3：找出需要该用户审查的 PR
    // 条件：
    // 1. 审查类型是"请求审查"（ReviewTypeRequest）
    // 2. 审查者是该用户，或者该用户在被请求的团队中
    // 3. 这是最新的审查记录（排除已经回应的）
    // 4. 排除用户自己创建的 PR
    subQuery := builder.Select("review.issue_id").
        From("review").
        Where(builder.And(
            builder.Eq{"review.type": ReviewTypeRequest},
            builder.Or(
                builder.Eq{"review.reviewer_id": reviewRequestedID},
                builder.In("review.reviewer_team_id", existInTeamQuery),
            ),
            builder.In("review.id", maxReview),
        ))
    
    // 最终条件：PR ID 在子查询结果中，且不是用户自己创建的
    sess.Where("issue.poster_id <> ?", reviewRequestedID).
        And(builder.In("issue.id", subQuery))
}
```

#### 第五步："我已审查" 的 SQL 逻辑

**文件位置**：`models/issues/issue_search.go:418-446`

```go
func applyReviewedCondition(sess *xorm.Session, reviewedID int64) {
    // 条件 1：排除用户自己创建的 PR
    notPoster := builder.Neq{"issue.poster_id": reviewedID}
    
    // 条件 2a：用户作为审查者提交过审查（批准/拒绝/评论）
    reviewed := builder.In("issue.id", builder.
        Select("issue_id").
        From("review").
        Where(builder.And(
            builder.Neq{"type": ReviewTypeRequest},  // 排除"请求审查"类型
            builder.Or(
                builder.Eq{"reviewer_id": reviewedID},
                builder.In("reviewer_team_id", builder.
                    Select("team_id").
                    From("team_user").
                    Where(builder.Eq{"uid": reviewedID}),
                ),
            ),
        )),
    )
    
    // 条件 2b：用户在 PR 中发表过评论（代码评论/审查评论）
    commented := builder.In("issue.id", builder.
        Select("issue_id").
        From("comment").
        Where(builder.And(
            builder.Eq{"poster_id": reviewedID},
            builder.In("type", CommentTypeComment, CommentTypeCode, CommentTypeReview),
        )),
    )
    
    // 最终条件：排除自己创建的，且（审查过 OR 评论过）
    sess.And(notPoster, builder.Or(reviewed, commented))
}
```

### 2. PR API 标识字段来源：主表 vs 扩展表

**重要更正**：PR API 响应中的 ID 字段**来自 PullRequest 扩展表**，而非 Issue 主表。

**PullRequest 扩展表结构**：`models/issues/pull.go:119-155`

```go

    ID              int64 `xorm:"pk autoincr"`   // 【扩展表主键】pull_request 表自增 ID
    IssueID         int64  `xorm:"INDEX"`        // 【外键】关联到 issue 表的 ID
    Index           int64                         // 【冗余字段】与 issue.index 保持同步
    HeadBranch      string
    BaseBranch      string
    HasMerged       bool
    // ... 其他 PR 特有字段
}
```

**Issue 主表结构**：`models/issues/issue.go:54-111`

```go
type Issue struct {
    ID              int64 `xorm:"pk autoincr"`   // 【主表主键】issue 表自增 ID
    Index           int64                         // 仓库内序号
    IsPull          bool                          // 区分字段
    PullRequest     *PullRequest `xorm:"-"`       // 关联的扩展数据指针
    // ... 其他共享字段
}
```

**PR API 转换时的 ID 字段赋值**：`services/convert/pull.go:74-77`

```go

    // ...
```

**两张表的 ID 关系总结**：

| 字段 | 来源表 | 说明 |
|-----|--------|------|
| `pr.ID` | `pull_request` 表 | PR 扩展表主键，全局唯一 |
| `pr.IssueID` | `pull_request` 表 | 外键，关联到 `issue.id` |
| `pr.Index` | `pull_request` 表 | 冗余字段，与 `issue.index` 相同 |
| `issue.ID` | `issue` 表 | 工单/PR 主表主键，全局唯一 |
| `issue.Index` | `issue` 表 | 仓库内序号，同一仓库内唯一 |

**API 响应示例**：
- `GET /repos/{owner}/{repo}/issues/123` → 返回的 `id` 是 `issue.id`
- `GET /repos/{owner}/{repo}/pulls/123` → 返回的 `id` 是 `pull_request.id`
- 两者的 `number` 字段（JSON 中的 `number`）都是 `Index`，值相同

```go
//   type: string
```

## 七、设计特点总结

### 1. 界面层设计原则

- **单模板复用**：工单和 PR 列表共用 `templates/repo/issue/list.tmpl` 模板
- **条件渲染**：通过 `PageIsPullList`、`IsPull`、`PullRequest.HasMerged` 等布尔字段控制显示差异
- **渐进式增强**：PR 特有信息（分支、审查状态、提交状态）通过 `{{if .IsPull}}` 条件块按需渲染

### 2. API 层设计原则

- **字段复用**：PR API 先转换为 Issue API，再追加 PR 特有字段
- **接口分离**：虽然底层数据共享，但 API 层面提供独立的 `/issues` 和 `/pulls` 端点
- **参数扩展**：PR 接口增加 `base_branch` 等特有过滤参数

### 3. 与共享模型的联动

- **数据驱动 UI**：所有界面差异最终都由底层数据字段（`IsPull`、`HasMerged`、`Status`）驱动
- **单一真相源**：状态判断逻辑集中在模型层（如 `GetLastEventLabel()`），界面层只需调用
- **懒加载优化**：`PullRequest` 扩展数据按需加载，避免查询工单时产生不必要的 JOIN

### 4. 与合并/关闭分叉的联动

- **状态联动**：合并操作通过 `SetMerged()` → `SetIssueAsClosed()` 链路同时更新两张表
- **UI 响应**：界面通过 `PullRequest.HasMerged` 字段自动感知合并状态，显示对应图标和文案
- **审计完整**：`CommentTypeMergePull` 和 `CommentTypeClose` 区分不同的关闭原因，保留完整操作历史
